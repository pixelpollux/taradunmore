# design-sync notes — taradunmore-ui

## Repo shape

This repo is a personal Next.js portfolio/blog, not a publishable component
package — there's no Storybook and no library `dist/` build. The synced
"design system" is the 7 files in `app/ui/` (8 components once `BrandIcons.tsx`'s
two named exports — `GithubIcon`, `LinkedinIcon` — are counted separately;
that file has no default export, so it doesn't land as one grouped
component). `cfg.srcDir` is `app/ui`.

- **`package.json` needed a `name` field.** The converter's `.d.ts`
  extraction (`lib/dts.mjs` `loadDts`) walks up from the source dir looking
  for the nearest `package.json` with a `name` field; without one it walks
  off the filesystem root and crashes (`ENOENT '/package.json'`). Added
  `"name": "taradunmore-ui"` to the repo's root `package.json` — harmless for
  a private app, required for design-sync to run at all. Don't remove it.
- **No dist → synth-entry mode.** Build is invoked with
  `--entry ./dist/index.js` (a path that doesn't exist) purely so the
  PKG_DIR directory-walk lands on the repo root without erroring; passing no
  `--entry` at all instead tries `node_modules/taradunmore-ui` (doesn't
  exist, since this repo IS the package). Keep passing `--entry ./dist/index.js`
  on every rebuild.
- **`.d.ts` prop extraction failed for all 8 components** (all show up as
  `[key: string]: unknown` without it) because every component types its
  props as an inline object literal, not a named interface. Hand-written
  `cfg.dtsPropsFor` entries cover all 8, transcribed from the real source
  prop types in `app/ui/*.tsx`. If any component's prop signature changes,
  update the matching `dtsPropsFor` entry too — it will NOT auto-update.

## CSS / tokens

- No compiled stylesheet exists in the repo (Next.js compiles Tailwind
  internally at build time). `cfg.cssEntry` points at
  `.design-sync/.cache/compiled-tailwind.css`, generated by `cfg.buildCmd`
  (`npx tailwindcss -i .design-sync/tailwind-entry.css -o .design-sync/.cache/compiled-tailwind.css --config tailwind.config.ts`)
  — **run buildCmd before every rebuild**, `resync.mjs` does this
  automatically but a bare `package-build.mjs` run does not.
- `.design-sync/tailwind-entry.css` (committed) is the actual Tailwind input:
  it `@import`s the real `app/globals.css` unchanged, then adds
  `--font-Fredoka` / `--font-cherry` custom-property definitions. Those two
  vars are normally injected at runtime by `next/font/google` via a
  generated className on `<html>` (Fredoka, `app/layout.tsx`) and the
  headline element (Cherry Bomb One, `app/page.tsx`) — absent when a
  component renders standalone outside the Next.js app, so they're
  redeclared here as literal family names instead.
- `.design-sync/brand-fonts.css` + `.design-sync/brand-fonts/*.woff2`
  (committed, wired via `cfg.extraFonts`): self-hosted copies of Fredoka and
  Cherry Bomb One, **latin subset only**, fetched directly from
  `fonts.gstatic.com` (same files Google Fonts serves, found via the legacy
  `fonts.googleapis.com/css?...&subset=latin` endpoint — the current `css2`
  endpoint no longer honors `subset=latin` and returns per-script splits
  instead). If the site ever adds non-Latin copy, this only covers Latin
  glyphs.

## Known render warns (triaged, non-blocking)

- `[TOKENS_MISSING] --nav-height` — referenced by a `scroll-mt-[var(--nav-height)]`
  utility class that Tailwind generated because `tailwind-entry.css`'s
  content globs scan all of `app/**` (matching the site's own
  `tailwind.config.ts`), not just `app/ui/`. No synced component uses this
  var; it comes from `app/blocks/HeaderNav.tsx` and friends, out of scope.
- `[TOKENS_MISSING] --tw-shadow-color` — Tailwind's own internal box-shadow
  variable, surfaced by `Button`/`Card`'s `hover:shadow-[...]` arbitrary
  values. No default is ever set for it in this codebase; only affects the
  `:hover` shadow color (falls back to no shadow on hover), not the resting
  appearance. Pre-existing in the site itself, not a sync artifact.
- **`Headline`'s `primary`/`secondary`/`tertiary` variants render identically
  to `default`.** `app/globals.css` only defines `.headline--highlighter` and
  `.headline--display` — there's no `.headline--primary/secondary/tertiary`
  rule at all. This is a pre-existing gap in the site's own CSS, not
  something to fix here; the prop values are real API surface (so kept in
  `Headline.d.ts`) but only `highlighter` and `display` currently look
  different. Didn't author a dedicated preview sweeping all three since
  they'd show three identical cards.
- **`GithubIcon`/`LinkedinIcon` have no default width/height.** The real
  usage in `app/blocks/homepageSections/ContactSection.tsx` renders `<Icon />`
  bare inside a `size-12` badge with no explicit sizing prop — relying on
  the SVG's intrinsic box. The authored `InBadge` previews pass explicit
  `width={24} height={24}` instead of reproducing this bare, to keep the
  card legible; see the inline comment in each preview file for why. Worth
  flagging to the site owner independently — this may be an existing bug in
  the live site too, not something design-sync introduced or fixed.

## Verification — NOT machine-checked

**No render check ever ran on this sync**, at the user's explicit choice (no
playwright/chromium installed; declined a local `http-serve` preview too).
`package-validate.mjs` ran with `--no-render-check` throughout. This means:

- None of the 8 authored previews (Avatar, Button, Card, CoverImage,
  DateDisplay, GithubIcon, Headline, LinkedinIcon) have been screenshotted,
  graded, or visually confirmed to render correctly — only confirmed to
  **compile** cleanly.
- `package-capture.mjs` (the absolute-grading step) never ran, so there are
  no `.design-sync/.cache/review/*.grade.json` verdicts backing this upload.
- The biggest actual risk, based on source inspection alone: `Avatar` and
  `CoverImage` both go through `lib/contentful-image.tsx` → `next/image`.
  `next/image`'s client implementation got fully bundled (confirmed via
  `grep getImgProps ds-bundle/_ds_bundle.js`) and *should* still render a
  plain `<img>` outside Next.js since a custom `loader` prop is passed
  (bypassing Next's image-optimization API route) — but this was never
  empirically confirmed in a browser.

**Next sync (or the user, right now) should install playwright + chromium,
or open `ds-bundle/.review.html` (`npx serve ds-bundle`) in a real browser,
and specifically check `Avatar` and `CoverImage` render their image, before
trusting this design system's visual fidelity.** Everything else (Button,
Card, Headline, DateDisplay, the icons) is plain DOM/SVG with no
comparable risk.

## Re-sync

Re-run `node .ds-sync/resync.mjs --config .design-sync/config.json --node-modules ./node_modules --entry ./dist/index.js --out ./ds-bundle --remote .design-sync/.cache/remote-sync.json` —
it re-runs `cfg.buildCmd` (recompiles Tailwind) automatically. Re-copy the
staged scripts first (`cp -r <skill-base-dir>/{package-build.mjs,package-validate.mjs,package-capture.mjs,resync.mjs,lib,storybook} .ds-sync/`) —
a stale `.ds-sync/` runs an old converter.
